## Project and method

An AI coding agent (GitHub Copilot) supervised with the **Architrave** agent workflow did this work: one
coordinator session (this branch) supervised a runtime/startup worker (side branch) and a private
composition-research worker (separate repo), with owner go/no-go decisions, per-lane experiment ledgers,
and honesty gates (no milestone claimed unless observed). Session canvases/dashboards were local and are not
persisted; the committed plan, ledgers and handovers are the record.

## Goal and hard limits

Run the **unchanged original Xbox PC app** under Wine/CrossOver on Apple silicon with a
visible window, real content, genuine sign-in and the real account library.
No replacement app, no forged identity/tokens/authentication/service results, no VM as the
product runtime, no credentials in the repo, no unscoped process kills.

## The wall

1. XAML renders through native dcomp **private partner interfaces** (`DeviceInternal {6b556968}`,
   `DesktopDevicePartner4 {d14b6158}`, `{e7894c70}`, VisualPartner, SurfaceFactoryPartner, Primitive/Color
   partners; ~10 interfaces, ~280 slots, static count from the XAML 26100 PDB). Wine has none of them.
2. The private composition worker built a standalone `Windows.UI.Composition` factory over staging
   classic dcomp (EXPERIMENT drop-ins v1 to v10). With it the app stays alive and walks the first
   frame, one new requirement per ~4-minute run.
3. Current gate (leading hypothesis, **not verified**): wined3d creates the Vulkan swapchain with
   "Image count 0", i.e. a 0x0 render target. `d14b6158` slot 7 (`CreateSurfaceFactory`) is never called
   in any run, so `DCompTreeHost::EnsureResources` is not reached or the D3D device is null.
   The earlier "headless null driver makes CoreWindow invisible" theory is **ruled out as the sole gate**:
   a real winemac window was shown (brG1) and forcing visibility (X-01) changed nothing.
4. Earlier superseded wrong theories (kept for history): "MRT/resource system is the gate" and
   "IsMain/theme lock". The real earlier gate was `RequestedTheme`, fixed with a Wine `dwrite`
   `IDWritePrivateTextAnalyzer` implementation.

## Next step (cheapest discriminating test)

1. Measure the window/Bounds/size the app and wined3d actually see (CoreWindow Bounds, HWND client rect,
   `DesktopWindowTarget` size, the D3D device creation result) at the NotifyDirty point.
2. Find why `CreateSurfaceFactory` (slot 7) is not called: is the D3D/D2D device null, or is
   `EnsureResources` skipped? Fix that, rerun the diagnostic walk (~4 min per cycle).
3. Keep adding only the partner slots the walk actually reaches (table in the composition repo).
4. Only after XAML submits a frame: obtain a real screenshot (fix Mac display/TCC first, see below),
   then attempt sign-in with the **owner entering their own credentials**, then the library.

## Provenance and licensing risks (decide before any release)

- Native Windows files copied from a Windows 11 x64 host (builds 26100/26300) were used as experiments:
  ICU 72.1.0.4, `Windows.Graphics.dll`, native `gameplatformservices.dll`, XAML resource DLLs, earlier native
  XAML/WinRT DLLs. Redistribution and licensing are **undecided**. Do not ship them.
- The composition POC is not Microsoft's compositor: flattened (scale/opacity baked, no clip/transform/
  animation/ShapeVisual), one Apple GL config, ~9/10 intermittent, needs staging dcomp patches.
- Real absences are not faked: the Gaming Services package is genuinely missing; ExtendedExecution
  (needs the ExecModel broker) and a ThreadPoolTimer worker failed and were recorded.
- Not done: independent code review of runtime patches, Wine conformance runs, confirmation on a native
  Windows/ARM VM (Parallels was unavailable). Per `AGENTS.md`, upstream Wine/wine-staging/Proton/ReactOS
  must be checked before any new Wine API implementation is kept.
